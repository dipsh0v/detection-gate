How a rule fails

✗ eventNot collected — the sensor never emits the event, so nothing can match
✓ event · ✗ fieldAbsent or renamed — the event arrives, but the field the rule reads is not in the schema
✓ event · ✓ field · ✗ dataSilent — the field exists, but nothing arrived in it during the window
✓ event · ✓ field · ✓ data · ✗ exceptionException broken — the rule fires, and fires too often, because an exclusion cannot apply

A rule fires only when all three links hold, and which link broke is also what decides who can fix it. The fourth row is not a break in the chain: those rules do fire, and fire too often, because an exclusion they rely on cannot apply.

Advisory · not measurement
what it is
Sysmon Event ID 23 (FileDelete) records a file deletion by a process, with the process image, user, target filename, hashes, and whether the file was archived. The original file is saved to the ArchiveDirectory.
how it is collected
Add a <FileDelete onmatch="include"> rule group to the Sysmon config (schema 4.30+, Sysmon 11+). Use onmatch="exclude" with no rules to log all deletes. Events go to Microsoft-Windows-Sysmon/Operational. Use <FileDeleteDetected> (event 26, Sysmon 13+) to log without archiving.
expected volume
Unfiltered, it is one of the highest-volume Sysmon events, since temp files, browser caches, and updaters delete constantly. Target-path includes (backup extensions, .evtx, IIS log directories) keep it manageable.
why it is missing
The config has no FileDelete rule group, or the Sysmon version predates event 23. Include rules may be too narrow. Archiving is on by default, so deleted files fill the ArchiveDirectory and can exhaust disk. Event 26 is a separate event ID.

what it is
Sysmon Event ID 3 (NetworkConnect) records DestinationHostname, a reverse-DNS (PTR) result for the destination IP. It is not the name the process asked for. Pipelines usually map it to destination.domain, and it is often empty.
how it is collected

Rules serving another log source leave the denominator, because counting them would inflate the result with problems this sensor was never responsible for. Rules this tool could not assess do not get that treatment: dropping them would shrink the denominator and raise the percentage on the strength of our own failures, so they are counted and named above.

The event and field checks are facts about configuration and schema: the sensor either emits an event or it does not, the schema either holds a field or it does not, and data either arrived in the window or it did not. Where a value's destination is marked derived, it was read out of a pipeline script and confirmed against the schema rather than declared by the pipeline as a rename; that is weaker evidence and the finding says so.

Field names are resolved through the same conversion pipeline used to deploy these rules. A different pipeline resolves different names and produces a different result, so this report describes the pipeline it was run with.

The event check asks whether the configuration collects an event at all. It does not evaluate how narrowly an include rule scopes that event, so a rule counted here as able to fire may still never see the activity it describes. 1813 of the rules in scope sit on an event this configuration collects only through include rules.

A rule can break in more than one way, so it may appear under more than one cause above. The cause counts are therefore not disjoint and do not sum to the headline.
